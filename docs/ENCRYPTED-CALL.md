# 加密通话：按 enigmaj 原理的对称实现

依据：`shared/enigmaj-re/REPORT.md`（反编译 + 双实例实测）。

## 1. enigmaj 的原始原理（报告 §7.2 / §8 实测）

enigmaj 本身**没有通话功能**，它提供的是「把端到端加密层架在普通私聊消息通道上」：

| 帧 | 载荷 | 语义 |
|---|---|---|
| `PQC_BEGIN\n<base64>` | ML-KEM-768 封装公钥 ek（1184 B → base64 1580 字符） | 发起方发出公钥 |
| `PQC_REPLY\n<base64>` | ML-KEM-768 密文 ct（1088 B → base64 1452 字符） | 响应方**收到即自动**封装并回发 |
| `ENC\n<base64>` | `nonce(12) ‖ ciphertext ‖ tag(16)` | AES-256-GCM 加密载荷 |

- 双方最终各自得到同一把 **32 B 共享密钥**（= ML-KEM 的 SS），实测两侧一致。
- 长度 ≤ 27 B 的 `ENC` 载荷直接判「密文长度不足」（= 12 nonce + 16 tag 的最小值）。
- 已有共享密钥时可跳过握手（原文案「已使用提供的共享密钥，无需握手」）。
- 密钥持久化在 `config.json → shared_secrets[对端UID] = base64(32 B)`。
- 无密钥时收到 `ENC` → 提示「收到来自 X 的加密消息，但无共享密钥」。
- 收到 `PQC_REPLY` 但没有对应私钥 → 按原样丢弃并记日志。

## 2. 对称实现（本客户端）

「加密通话」= 用上述同一套帧做**会话建立 → 保活 → 会话结束**，双方逻辑完全对称：

| 阶段 | 发起方 | 响应方 |
|---|---|---|
| 拨出 | 生成临时密钥对 → 发 `PQC_BEGIN`（状态：握手中） | — |
| 来电 | — | 收到 `PQC_BEGIN` → 封装 → **立即回 `PQC_REPLY`**（状态：已连接 · 响应方） |
| 接通 | 收到 `PQC_REPLY` → 解封装 → 32 B SS（状态：已连接 · 发起方） | 同上 |
| 通话中 | 每 15 s 发 `ENC{"t":"ping"}`；收到 `ping` 回 `pong` | 同左（完全对称） |
| 挂断 | 发 `ENC{"t":"end"}` → 本地结束 | 解出 `end` → 同样结束 |
| 掉线 | 45 s 内收不到任何帧 → 判定「心跳超时」结束 | 同左 |

- 帧格式、载荷布局、最小长度校验、持久化语义与 enigmaj **逐字对齐**。
- 本地已有该对端密钥时也可直接开始（发 `ENC{"t":"start"}` 通知对端），对应「无需握手」。
- 既有 `/direct/send` 通道承载帧（enigmaj 也是把帧当普通 message body 发）。
- 帧**不会**出现在聊天气泡里，也不写入消息缓存；自己发出的回显被显式排除。

## 2.5 通话内的文本消息也是加密的（2026-09-13 补齐）

enigmaj 的**发消息入口**本身就是「查密钥 → 加密 → 发送」（报告 §4，`0x1101818`；§7.3 实测：
用户输入 `secret-message-1` 后线上出现的就是 `ENC\n<60 字符 base64>`）。本客户端现在照此实现：

| 环节 | 行为 |
|---|---|
| 已接通（有密钥） | 输入框文本 → `MessagePayloadBuilder.buildBody()` 生成 v2 JSON → **整段 JSON 用 32B SS 加密** → `ENC\n<base64>` → 仍走 `POST /v1/direct/send`（字段不变：`to_uid/body/msg_type`） |
| 未通话 | 原样明文 v2 JSON（与 enigmaj「没有必须加密的策略」一致） |
| 握手中（还没密钥） | 文本**入队暂存**，状态栏提示「正在建立加密通道，N 条消息将在接通后加密发送」；接通即自动加密补发；若通话最终没建立则明文补发（不丢消息） |
| 可加密的载荷 | 文本（含引用）；**媒体/表情/红包仍走各自接口的明文**（本版范围外） |
| 入站分流 | 网络层按载荷内容区分：JSON 含 `t` → 控制帧（ping/pong/start/end，通话层消费）；否则 → 普通消息（解出明文交给消息管线） |
| 本地展示/缓存 | 存的始终是**明文 v2 JSON**（气泡、通知、会话预览、历史回源全部无感复用）；气泡加一个小锁标记 |
| 历史回源 | `mergeMessages` 会把 ENC 消息帧解包后照常展示；握手帧/控制帧/解不开的帧一律丢弃 |

所以：**加密通话下，单聊界面发送的文本消息 = 走同一个消息发送接口、body 换成 ENC 帧的加密消息。**

## 3. 与 enigmaj 的差异（有意为之，代码内均有注释）

1. **KEM**：enigmaj 用 aws-lc-rs 的 ML-KEM-768。本客户端优先用 BouncyCastle 的
   ML-KEM-768（`bcprov-jdk18on`，反射调用）；依赖缺失/类名不符时**自动降级
   ECDH P-256 + SHA-256**（仍得 32 B SS）。两种 KEM 的帧格式完全相同，
   接收端按公钥长度自动识别（1184 → ML-KEM-768，91 → P-256）。
2. **不含音频**：本版是「加密会话通道」（握手 + 心跳 + 挂断），音频管线未接入。
   UI 因此只说「加密通话中」，不假装在传语音。
3. 共享密钥落盘即时（enigmaj 只在正常退出时写回 `config.json`）。

## 4. 涉及文件

- `core/e2e/E2eCrypto.kt` —— 帧前缀与载荷编解码、`E2eKem` 抽象、
  `MlKem768Kem`（BC 反射）、`EcdhP256Kem`（降级）、`E2eAead`（AES-256-GCM）、密钥指纹。
- `core/e2e/E2eKeyStore.kt` —— 每对端共享密钥持久化（`shared_secrets` 等价物）。
- `core/e2e/EncryptedCallManager.kt` —— 通话状态机（Idle/Establishing/Connected/Ended）、
  心跳与超时、`KemFactory`。
- `OldChatApplication.kt` —— 通话管理器挂在进程级（离开会话页不中断通话）。
- `feature/chat/ChatViewModel.kt` —— `startEncryptedCall/hangUpEncryptedCall/dismissCallResult`，
  入站帧拦截（含自回显排除）。
- `feature/chat/ChatScreen.kt` —— 附件抽屉第 4 个按钮「加密通话」、通话状态栏、
  挂断确认弹窗。

## 5. 界面行为

- 抽屉内 `🔒 加密通话` 点击 → 开始呼叫（或直接接通，若已有密钥）。
- 通话开始即自动进入**全屏通话页**：锁形图标、对端昵称、状态（握手中/通话中）、
  通话计时、以及可验证的握手信息（算法 / 共享密钥指纹 / 密钥来源 / 本次角色：发起方或响应方）。
- 通话页两个按钮：`返回聊天`（收起为顶部状态栏，聊天照常可用）、`结束通话`
  （红色，点击先弹确认框）。
- 抽屉里同一个按钮在通话中变为红色 `📵 结束通话`；**再次点击同样先弹确认框**，
  确认后才发 `ENC{"t":"end"}` 并退出 —— 这就是「再次点击并确认后退出」。
- 收起后的顶部状态栏：握手中（显示算法）/ 通话中（时长 + 密钥指纹 + 是否复用旧密钥）
  / 已结束（原因，3 秒后自动收起）；点「通话页面」可重新展开全屏。
- 通话状态挂在进程级：切走会话页不会中断通话；重新进入该会话仍能看到状态。
- 发起方 30 秒内收不到 `PQC_REPLY` → 自动结束并提示「对方未响应」。

## 6. 真机验证建议

1. 两端登录不同账号，进入同一单聊，A 点「加密通话」→ B 应自动出现状态栏（响应方）。
2. 对比两侧「密钥指纹」是否一致 —— 一致即证明握手成功（等价 enigmaj 的
   `shared_secrets` 双方一致这一实测结论）。
3. A 点「结束通话」→ B 应在 1~2 秒内显示「对方结束了加密通话」。
4. 检查聊天记录里**没有** `PQC_BEGIN/PQC_REPLY/ENC` 字样的气泡。
